# Generic device CAN integration

The generic v0.1.0 firmware is a **Cyphal/CAN device** running the shared libcanard stack at 500 kbit/s arbitration / 2 Mbit/s data. Generated OpenSimGear DSDL transfers replace the old private CAN frame codec. Both sockets use the existing 4P4C wiring: 1=BUS_12V, 2=CAN_H, 3=CAN_L, 4=GND. Endpoint termination and cable/current qualification remain hardware requirements.

## Discovery and reports

The device operates independently of a gateway: it selects a Cyphal transport node ID, publishes the standard `uavcan.node.Heartbeat.1.0` message, and responds to `uavcan.node.GetInfo.1.0` with the name `org.opensimgear.device` and its stable unique ID. Transport node IDs are separate from the gateway's logical CAN routes 1–32 and its ordered USB controllers. Automatic node-ID selection is provided by the pinned Cyphal 1.1 libcanard implementation; it is not a private gateway allocation service.

The module identity is 16 bytes: ASCII `OSGD` followed by the MCU's 12 raw UID bytes. Its USB serial remains the original 24 hexadecimal UID characters. The module commits a fresh nonzero boot counter before starting its announcement loop. The typed capability announcement repeats at a nominal 500 ms (450–550 ms with identity/session seeded jitter) and includes the enabled HID profile, direct USB ownership, boot session and runtime configuration generation. A changed configuration generation renews the gateway lease and invalidates queued input even when HID shape stays identical; it does not change the profile schema revision. A matching gateway returns a logical CAN route, lease and gateway epoch in a typed assignment transfer. New compatible identities also automatically append an enabled USB controller; remembered disabled devices retain their choice and remain reachable for configuration. The device records the assigning gateway's actual Cyphal source node ID and rejects assignment/ACK transfers from another source while that route is live. An unchanged live assignment is idempotent; a new lease rearms acquisition. Assignment absence for 2 s invalidates the route and returns to discovery.

CAN input uses the same report layout as direct USB: up to 128 logical button bits, four packed hats and eight unsigned 16-bit axes, at most 34 bytes. All supplied profiles are lossless; no controls are silently removed. Invalid profiles fail before attachment. Unused padding is zero, and hats use 8 for neutral. Typed input normally refreshes every 10 ms while a current CAN assignment owns the route. A new route first sends neutral and requires fresh input acquisition.

## Ownership and encoder delivery

Mounted, awake direct USB has priority. While it owns input, announcements advertise `direct_usb=true` and the gateway neutralizes the enabled controller. Detach/suspend allows a fresh CAN fallback. Each ownership transition discards queued encoder events and stale report acknowledgements, clears pending CAN traffic through a bounded controller reset, then rearms held controls. Normal ownership changes restart immediately and send a priority ownership announcement. A real bus fault or failed restart waits 1 s before retrying. The direct USB HID completion behavior and retained-packet caveat in [README](README.md) still apply.

After assignment, `opensimgear.input.Status.1.0` independently confirms the current identity, source, boot and lease every 500 ms, including direct USB ownership and periods with no HID report. This is route liveness, not a USB completion acknowledgement. Disabled gateway controllers remain reachable for configuration and device actions without an enabled HID collection.

Successful CAN transmission does not acknowledge an encoder pulse. The module waits for the typed input acknowledgement emitted only after the gateway's actual USB HID completion. ACK must come from the assigned gateway source and match the current boot, logical CAN route and lease; its sequence and exact report must be present in the bounded 16-report transmit history. Duplicate, older, unknown and mismatched acknowledgements are rejected. Each encoder phase records a minimum input sequence, so a delayed ACK for an earlier same-direction press cannot acknowledge a later press. Press and release hold times start only after their corresponding completion ACK. If USB delivery stalls, encoder queues remain bounded and phases wait; there is no synthetic delivery credit.

The application stack emits extended FD+BRS frames. Hardware accepts all extended data frames so standard Cyphal messages, services and automatic node-ID selection can reach libcanard; classical CAN and FD frames without BRS are also received. RX processes at most four frames per loop. libcanard performs transfer-ID handling, duplicate suppression, multi-frame CRC validation and reassembly before application processing. Its bounded transmit queue retains transfers while the board queue is full. The 32-frame board transmit queue retains each transfer's deadline, discards expired queued frames, and cancels an expired active mailbox before reusing its queue head. Live frames permit at most three attempts, 20 ms retry spacing and 20 ms mailbox timeout; cancellation that cannot complete within 20 ms triggers recovery. Ownership/recovery resets purge both transport and board queues. Bus-off invalidates assignment and re-enters discovery after recovery. A transport node-ID collision invalidates the logical route and transmit history, purges old-source frames from the controller, and forces discovery under the newly selected Cyphal ID. Traffic from an old gateway source/lease/session cannot advance encoders. Lease ordering is checked within the current gateway epoch, and timeout/reset clears that scope. The protocol does not authenticate bus participants.

## Boot freshness and memory

The last two 2 KiB flash pages, at `0x0801F000` and `0x0801F800`, contain a CRC-protected two-page boot journal. The commit marker is programmed last. One interrupted write preserves the prior valid record; the next successful boot advances from it before announcing. A virgin all-FF journal starts at session 1. Corruption with no valid record, an exhausted counter, or failed erase/program causes a fail-closed fault with CAN standby asserted. Boot writes consume flash endurance; no write occurs per report or discovery.

Firmware code is restricted to 120 KiB flash and uses guaranteed 128 KiB SRAM, reserving 16 KiB stack and 512 bytes heap. Linker assertions prevent overlap with storage. Preserve the boot pages when programming an application update. If a full flash erase resets boot history, power-cycle the entire chain before resuming so no cached session remains. A separate settings journal at `0x0801E000` and `0x0801E800` stores the complete validated runtime input configuration and axis calibration in a canonical 598-byte record. The original final pages still store only boot freshness. Preserve both journals during application programming.

Erased settings receive a committed factory baseline at generation 1 before configuration commands are served. The first user save therefore preserves that baseline when an erase/program operation is interrupted. Initialization can retry a torn baseline only if the first page contains cleared bits belonging to the exact factory image, its commit marker is incomplete and the second page is erased. A complete marker with invalid data and other corrupt nonblank settings fail closed. Saved settings restore on reboot; writer claims and drafts do not. A different firmware factory image during an interrupted baseline may require explicit storage recovery rather than automatic replacement.

## Runtime configuration delivery

The matching gateway forwards bounded configuration commands over dedicated Cyphal subjects. The device accepts them only for its current identity, boot, gateway source, route, lease and epoch. Chunk assembly and reply buffers are bounded; an immutable cached reply prevents a retry from repeating a completed mutation. After a valid Apply, both transport and board transmit queues drain before direct USB detaches, acquisition and old completions are invalidated, and the new profile is announced. Descriptor/report shape remains neutral through the gateway until its stored profile matches the new announcement and the gateway layout is explicitly applied. See the [runtime contract](https://github.com/opensimgear/protocol/blob/main/serial/runtime-configuration.md).

The same bounded request/reply envelope carries `action describe`, `action state` and `action invoke` to a separate action dispatcher. A successful transport response contains `OK` followed by the action JSON; action validation failures stay inside that JSON. The current board advertises a readable `led.status.set_mode` enum (`auto`, `on`, `off`). The simulator advertises RGB and boolean LED setters through the identical production registry. Commands require the advertised catalogue revision and valid typed arguments, but no configuration claim. They never save settings, alter HID, or renew a lease. A duplicate complete request returns its original reply without executing again. LED mode persists across ownership changes; reboot restores `auto`. Suspend forces the physical LED off until resume. Software readback confirms the selected driver state, not an electrical measurement.
